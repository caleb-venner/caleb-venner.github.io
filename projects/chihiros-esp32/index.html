Replacing an aquarium light's Bluetooth controller with an ESP32

The light could only be controlled from the vendor's phone app. I traced its LED driver board, pulled out the factory Bluetooth module, and wrote ESP-IDF firmware in C to drive it myself.

Caleb Venner · November 2026 · Code on GitHub

The Chihiros WRGB II Pro is a four-channel aquarium light, with red, green, blue and white LED strings. Out of the box, the only way to control it is the vendor's phone app over Bluetooth.

My first attempt at fixing that was AquaBle, a Home Assistant integration that speaks the factory controller's Bluetooth protocol. It works, but it still depends on a Bluetooth link to a closed controller I can't see inside. What I really wanted was the light on my network as a device I fully understood, with its daily schedule running on the device itself.

That turned a protocol problem into a hardware one. I needed to find the signals the factory controller uses to drive the LEDs, then produce them from my own board without damaging the light.

Opening it up

Chihiros publish no schematic, so I had to build one up from the board itself. The factory controller turned out to be a small daughterboard carrying a Nordic nRF52832, which plugs into the driver board through two 10-pin headers.

I started by mapping each header pin back to the nRF52832 by continuity. That quickly separated power, ground and the SWD debug pins from everything else.

Next I identified the driver ICs from their markings. Red and green each use a PT4121 constant-current controller switching an external MOSFET. Blue and white each use an MK4025, which has its switch built in.

Then I traced each control line from a header pin, through a series resistor of about 200 Ω, to a driver's dimming input. Of the twenty header pins, only four turned out to matter.

Before connecting anything, I checked that the signals would actually be compatible. The PT4121 datasheet specifies PWM dimming from 100 Hz to 20 kHz with a logic-high threshold of 2.5 V, so a 3.3 V GPIO at 1 kHz can drive it directly with no level shifting. The MK4025 has no public datasheet, so I treated blue and white as the riskier pair until I'd seen them dim in proportion to the duty cycle.

The full pinout, component list and measurements are in the repository's hardware notes.

The new design

The plan was to leave as much of the original light alone as possible. The driver board keeps its own current regulation, and the ESP32-S3 only decides each channel's duty cycle.

Getting there meant solving three problems, none of which were obvious from the outside.

The board can't power an ESP32

The obvious move was to power the ESP32 from the 3.3 V pin that used to feed the Bluetooth module. Tracing that rail showed a buck converter stepping 36 V down to about 5 V, followed by a small linear regulator sized for a module drawing around 15 mA. An ESP32 with Wi-Fi active peaks at several hundred milliamps, which that regulator can neither supply nor dissipate. So the ESP32 gets its own buck converter from the 36 V input, with a shared ground.

Full brightness would overload the power supply

The vendor app lets each channel go up to "140%". Using the per-channel voltage and current figures from the app's power profile, all four channels at 140% come to about 187 W of LED load. The power supply is rated for 127 W. The app gets away with this by keeping a software power budget.

Full-scale PWM corresponds to that 140% point, so rather than reimplementing the budget, I capped the firmware. In my API, 100% maps to 100/140 of full duty, about 71%, and at that cap every channel at 100% together comes to about 120 W. The limit holds for any combination of requests, and there's no budgeting logic to get wrong.

The LEDs flashed at power-on

Some ESP32 pins are driven or pulled during boot, which would flash the light at full brightness for a moment every time it started. The four outputs avoid the ESP32-S3's strapping pins and use pins that stay low through the bootloader. The PWM channels are also set to 0% before the network or the scheduler starts.

The firmware

The firmware is about 700 lines of C on ESP-IDF, built with PlatformIO. I split it into small modules that each do one job.

The LED driver sets up four LEDC PWM channels at 1 kHz and 13-bit resolution. Every request goes through a single function that scales and caps the duty, so nothing else in the code can push a channel past the safe limit.

The scheduler is a FreeRTOS task. It either holds a manual colour or interpolates between up to 24 daily keyframes, including across midnight. Time comes from SNTP, and the light stays dark until the clock is valid rather than guessing.

The REST API has JSON endpoints to read the current state, set a colour, or upload a schedule. Input is range-checked as it comes in, and the schedule is saved to NVS so it survives a power cut. A daily schedule looks like this:

curl -X POST -H "Content-Type: application/json" -d '{
  "mode": "auto",
  "keyframes": [
    { "time_min": 780,  "r": 0,  "g": 0,  "b": 0,  "w": 0 },
    { "time_min": 810,  "r": 40, "g": 20, "b": 45, "w": 25 },
    { "time_min": 1230, "r": 40, "g": 20, "b": 45, "w": 25 },
    { "time_min": 1320, "r": 0,  "g": 0,  "b": 0,  "w": 0 }
  ]
}' http://192.168.1.50/api/state

Ramp up over 30 minutes from 13:00, hold, then fade out by 22:00.

For reliability, a task watchdog reboots the chip if the main loop hangs, and the outputs restart at 0%. Firmware updates go over the air into a two-slot partition layout, so I never have to open the light again to change the code.

Where it stands

The controller has run the light on my tank every day for a couple of months, with the factory module removed. Four-channel PWM with the duty cap, manual and scheduled modes, persistence across power cuts, network time, watchdog recovery and over-the-air updates all work.

It has known limits. The API has no authentication, so it belongs on a trusted network. Wi-Fi credentials are compiled in. Scheduled fades step in whole percentages rather than using the PWM's full 13-bit resolution, so long fades at low brightness move in small discrete steps.

Next, I want to replace the perfboard, buck module and jumper wires with a single PCB that has its own 36 V buck converter and plugs straight into the J1 and J2 headers. That should be small enough to fit back inside the light's original housing, so the whole thing goes back together like a factory part.
